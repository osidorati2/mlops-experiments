# Эксперимент: память worker-процессов FastAPI

Учебный сервис показывает, как растёт память контейнера при увеличении числа
uvicorn workers, если каждый worker загружает свою копию «модели».

## Что внутри

```
app/main.py               FastAPI-приложение
Dockerfile                образ (python:3.12-slim, uvicorn, WORKERS из env)
scripts/common.sh         общие лимиты: --cpus=2 --memory=1g --memory-swap=1g
scripts/run.sh N          запуск контейнера с N workers, ожидание загрузки модели
scripts/stop.sh [N...]    остановка контейнеров
scripts/measure_memory.sh снимок памяти контейнера (docker stats, cgroup, RSS/PSS процессов)
scripts/load_test.py      ограниченный нагрузочный тест (stdlib)
scripts/run_experiment.sh полный прогон 1 → 2 → 4 workers (с повторами), результаты в results/
scripts/summarize.py      сводка по каталогу results/<timestamp>: каждый запуск + среднее ± stdev
scripts/make_archive.sh   чистый архив проекта для сдачи (без __pycache__, .DS_Store, __MACOSX)
```

### Приложение

- **Модель.** В `lifespan` каждый worker выделяет `bytearray` на 128 MiB
  (`MODEL_SIZE_MIB`) и заполняет его ненулевыми байтами. Без записи ядро
  выдало бы «ленивые» нулевые страницы, и они не попали бы в RSS.
  Время загрузки, PID и PPID пишутся в лог.
- **`GET /health`**: статус, PID, загружена ли модель.
- **`GET /work`**: детерминированная CPU-работа без `sleep`: `WORK_ROUNDS`
  (по умолчанию 2000) итераций SHA-256 и 20 000 чтений из буфера модели.
  На каждый запрос уходит одинаковый объём работы, порядка нескольких мс.
  Функция синхронная (`def`), поэтому FastAPI выполняет её в threadpool и
  event loop не блокируется.
- uvicorn с `--workers N` запускает workers через `multiprocessing` в режиме
  **spawn**: каждый процесс заново импортирует приложение и сам загружает модель.
  Copy-on-write между ними нет.

## Запуск

```bash
docker build -t worker-mem-exp:latest .

# одинаковые лимиты для всех вариантов (см. scripts/common.sh):
#   --cpus=2 --memory=1g --memory-swap=1g --pids-limit=256
./scripts/run.sh 1     # http://127.0.0.1:8001
./scripts/run.sh 2     # http://127.0.0.1:8002
./scripts/run.sh 4     # http://127.0.0.1:8004
```

Эквивалент без скриптов:

```bash
docker run -d --name mem-w2 --cpus=2 --memory=1g --memory-swap=1g --pids-limit=256 \
  -e WORKERS=2 -p 127.0.0.1:8002:8000 worker-mem-exp:latest
docker logs -f mem-w2        # строки "model loaded ... pid=..."
```

Контейнеры лучше запускать **по одному**: если запустить все три сразу, они
будут конкурировать за CPU хоста, и замеры станут непоказательными.
`run_experiment.sh` делает это автоматически.

## Измерение памяти

```bash
./scripts/measure_memory.sh mem-w2
```

Скрипт выводит:

| Источник | Что означает |
|---|---|
| `docker stats` | usage минус неактивный page cache, то есть то, что показывает Docker |
| `memory.current` | вся память cgroup контейнера (anon + page cache + kernel); именно с ней сравнивается лимит 1 GiB |
| `memory.peak` | пик с момента старта контейнера, включая загрузку модели |
| `memory.stat anon/file` | анонимная память (буферы, heap Python) и файловый кэш |
| `events.oom_kill` | сколько раз внутри контейнера срабатывал OOM-killer |
| RSS / PSS по процессам | RSS считает общие страницы библиотек в каждом процессе, PSS делит их между процессами |

Ручные команды:

```bash
docker stats --no-stream mem-w2
docker exec mem-w2 cat /sys/fs/cgroup/memory.current /sys/fs/cgroup/memory.peak
docker exec mem-w2 grep -E '^(anon|file) ' /sys/fs/cgroup/memory.stat
docker inspect -f '{{.State.OOMKilled}}' mem-w2
```

## Нагрузочный тест

```bash
python3 scripts/load_test.py --url http://127.0.0.1:8002 --requests 1000 --concurrency 8
# или по времени: 60 с основного замера (максимум 120 с)
python3 scripts/load_test.py --url http://127.0.0.1:8002 --duration 60 --concurrency 8
```

Нагрузка всегда **конечна**. Есть два режима основного замера:

| Режим | Флаг | Граница |
|---|---|---|
| по числу запросов (по умолчанию) | `--requests N` | 1…5000 запросов |
| по времени | `--duration S` | 0 < S ≤ 120 с; если задан, `--requests` игнорируется |

В обоих режимах конкурентность фиксирована (`--concurrency`, 1…32), прогрев —
не дольше 30 с. Значения вне границ скрипт отклоняет. На выходе: RPS,
p50/p95/p99, ошибки, доля ошибок и распределение запросов по PID workers.
Каждый запрос открывает новое соединение, поэтому видно, как ядро распределяет
`accept()` между процессами.

**Критерий успеха:** есть хотя бы один успешный ответ и доля ошибок не больше
`--max-error-rate` (по умолчанию 0 — любая ошибка = провал). При провале код
завершения 1, в JSON `"passed": false` и `"fail_reason"`. Сводка печатается и
сохраняется (`--json-out`) в любом случае. Отсутствующие измерения (например,
процентили без единого успешного ответа) записываются как `null` — JSON всегда
стандартный, без `NaN`.

### Прогрев

Порядок замера:

1. `run.sh` запускает контейнер и ждёт готовности не дольше `READY_TIMEOUT`
   (90 с). Готовность — это ровно N **живых** worker-процессов (по `/proc` внутри
   контейнера), и у **каждого из них** в логе есть `model loaded ... pid=<его PID>`.
   Строки умерших процессов не засчитываются, поэтому перезапуски workers после
   OOM не дают ложной готовности. Дополнительно `/health` должен ответить; у curl
   таймаут 2 с.
2. `load_test.py` в течение `--warmup-seconds` (по умолчанию 7 с, максимум 30)
   шлёт запросы с той же конкурентностью, что и основной замер (8). Это
   прогрев. Его результаты отбрасываются, в stderr выводится только краткая
   сводка: число запросов, ошибки и какие PID ответили.
3. Статистика начинается с нуля, и идёт основной замер (`--requests` или `--duration`).

```bash
python3 scripts/load_test.py --url http://127.0.0.1:8002 --warmup-seconds 10   # дольше
python3 scripts/load_test.py --url http://127.0.0.1:8002 --warmup-seconds 0    # без прогрева
```

В `run_experiment.sh` длительность задаётся переменной `WARMUP_S`. Там прогрев
идёт **отдельным вызовом** (`load_test.py --warmup-only`), чтобы граница
основного замера была точной: снимки счётчиков cgroup и сэмплер памяти
относятся только к основному интервалу.

## Полный прогон

```bash
./scripts/run_experiment.sh                                  # 1, 2, 4 workers, 1 запуск, 1000 запросов
RUNS=3 DURATION=60 CONCURRENCY=8 ./scripts/run_experiment.sh  # 3 запуска по 60 с на конфигурацию (~13 мин)
REQUESTS=500 CONCURRENCY=8 ./scripts/run_experiment.sh 4
```

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `RUNS` | 1 | повторов на конфигурацию, каждый в свежем контейнере |
| `DURATION` | 0 | длительность основного замера, с; при 0 используется `REQUESTS` |
| `REQUESTS` | 1000 | число запросов основного замера, если `DURATION=0` |
| `CONCURRENCY` | 8 | параллельных клиентов (и в прогреве, и в замере) |
| `WARMUP_S` | 7 | длительность прогрева, с |
| `SETTLE_S` | 5 | пауза после готовности перед замером памяти в простое |

Для каждого N и каждого повтора скрипт делает следующее:

1. свежий контейнер, ожидание готовности, пауза `SETTLE_S`;
2. замер в простое (`idle.txt`);
3. прогрев (отдельный вызов, результаты отбрасываются);
4. снимок `cpu.stat` + `memory.events` (`cg-before.txt`);
5. основной замер, параллельно сэмплер `memory.current` раз в 0,5 с
   (`samples.txt`, не дольше ~5 мин);
6. снимок `cpu.stat` + `memory.events` (`cg-after.txt`);
7. замер после нагрузки (`after.txt`), логи, остановка.

Отдельный контейнер на каждый повтор нужен, чтобы `memory.peak` и счётчики не
переносились между запусками.

### Границы метрик в сводке

| Колонка | Интервал |
|---|---|
| `idle` | момент после готовности, до прогрева |
| `main max` | максимум `memory.current` **только за основной замер** |
| `peak` | `memory.peak` **за всё время жизни** контейнера: старт, загрузка модели, прогрев, замер |
| `cpu`, `thr %`, `thr s` | разность `cpu.stat` до/после **основного замера**: использованные ядра, доля периодов с throttling, время throttling |
| `oom main` | прирост `memory.events oom_kill` за основной замер |
| `oom tot` | `oom_kill` за всё время жизни контейнера |
| `restart` | сколько раз workers загружали модель сверх N, то есть перезапуски |

OOM учитывается по счётчику cgroup, а не только по флагу Docker `OOMKilled`:
если OOM-killer убьёт отдельный worker, родительский uvicorn продолжит работать
и перезапустит его, а `OOMKilled` останется `false`. Источники берутся все
доступные: `oom_kill` из `cg-after.txt`, `events.oom_kill` из `idle.txt` и
`after.txt` (резерв, если снимок cgroup потерян), флаг `OOMKilled`.

Колонка `status` в сводке: `ok`, либо комбинация `FAIL` (нагрузочный тест не
прошёл), `OOM` и `INCOMPLETE`. `INCOMPLETE` означает, что нет обязательных
метрик: счётчиков `cpu.stat`/`memory.events` до или после замера, `memory.current`
в простое, сэмплов памяти, `memory.peak`, логов или флага `OOMKilled`. Список
недостающих метрик печатается под таблицей. Такой запуск считается неуспешным.

### Ошибки и уборка

- Обработчик `trap` на `EXIT`/`INT`/`TERM` останавливает нагрузочный тест и
  сэмплер, удаляет флаг сэмплера, сохраняет `logs.txt` и `state.txt`
  (OOMKilled, ExitCode) текущего запуска и удаляет его контейнер. Исходный код
  ошибки сохраняется (Ctrl+C → 130, SIGTERM → 143).
- Нагрузочный тест работает в фоне под `wait`, поэтому сигнал прерывает замер
  сразу, а не после его окончания.
- Если провалился нагрузочный тест, запуск доводится до конца (замеры, логи),
  выполняются остальные запуски, а скрипт возвращает код первого провала и
  пишет `failed runs: ...` в `summary.txt`.
- Если снимок метрик не удался, скрипт печатает `WARNING` и продолжает
  собирать диагностику, но запуск попадёт в сводку как `INCOMPLETE`.
- Если тесты прошли, но сводка нашла OOM или неполный запуск, код завершения 1.

Файлы лежат в `results/<timestamp>/w<N>-r<R>-*`, итог — в `summary.txt`.
Его можно пересчитать: `python3 scripts/summarize.py results/<timestamp>`.

## Ожидаемый результат (оценка до замеров)

Локальный прогон на macOS дал RSS ≈ 165 MiB на worker
(128 MiB модели + ~35 MiB интерпретатора с FastAPI) и ≈ 18 MiB на
родительский процесс uvicorn. Для контейнера ориентировочно:

| workers | процессы | ожидаемо `memory.current` |
|---|---|---|
| 1 | 1 (без supervisor'а) | ~170 MiB |
| 2 | parent + resource_tracker + 2 | ~360 MiB |
| 4 | parent + resource_tracker + 4 | ~700 MiB (≈ 70% лимита) |

Память растёт линейно: примерно на `N × (размер модели + накладные расходы
Python)`. По замеру (см. «Фактические результаты») это ≈ 30 MiB + N × 159 MiB: при 6 workers
≈ 985 MiB, вплотную к лимиту 1 GiB, а при 7 или с моделью побольше лимит будет
превышен, и сработает OOM-killer. Его видно по `OOMKilled=true` или по
росту `oom_kill` / колонке `restart` в сводке.

При 2 CPU пропускная способность растёт с 1 до 2 workers. С 4 workers, скорее
всего, роста почти не будет: CPU-квоты всего на 2 ядра, а памяти уходит вдвое
больше.

## Фактические результаты

Прогон `results/20261025-204552`: `RUNS=3 DURATION=60 CONCURRENCY=8 WARMUP_S=7`,
лимиты 2 CPU / 1 GiB, Docker Desktop 27.4 на macOS (cgroup v2). Все 9 запусков
успешны: 0 ошибок, `oom_kill` = 0, перезапусков workers нет. Значения —
среднее ± stdev по 3 запускам; границы колонок описаны в разделе «Границы метрик
в сводке».

| workers | idle, MiB | max за замер, MiB | peak за жизнь, MiB | RPS | p50, мс | p95, мс | p99, мс | CPU, ядер | throttling, % периодов | `/work` на сервере, мс |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 160.7 ± 0.1 | 162.1 ± 0.2 | 163.4 ± 0.4 | 212.1 ± 0.3 | 36.8 | 45.5 | 61.8 | 1.00 | 0.0 | 4.4 |
| 2 | 348.6 ± 0.1 | 350.4 ± 0.2 | 352.6 ± 0.7 | 375.3 ± 1.9 | 19.8 | 34.0 | 113.0 | 1.83 | 6.8 ± 1.8 | 4.5 |
| 4 | 666.3 ± 0.1 | 669.3 ± 0.1 | 672.9 ± 0.5 | 358.2 ± 5.3 | 12.1 | 65.4 | 111.6 | 1.93 | 92.0 ± 0.6 | 9.0 |

Выводы:

- **Память растёт линейно**, ≈ 30 MiB + N × 159 MiB при N ≥ 2. Это родительский
  uvicorn (~20 MiB PSS) и `resource_tracker` (~11 MiB) плюс по ~159 MiB на worker:
  128 MiB буфера и ~30 MiB интерпретатора с FastAPI. При N = 1 отдельного
  родителя нет. Нагрузка добавляет лишь 2–3 MiB: память определяется копией
  модели в каждом процессе. 4 workers занимают ~65% лимита, 6 — по расчёту
  ≈ 985 MiB, 7 уже не поместятся.
- **Пропускная способность упирается в 2 CPU.** 1 → 2 workers: +77% RPS, один
  процесс Python не занимает больше одного ядра. 2 → 4: RPS −5%, контейнер
  использует 1,93 ядра из 2, throttling в 92% периодов основного замера. Тот же
  `/work` выполняется вдвое дольше (9,0 мс против 4,5), потому что 4 процесса
  делят 2 ядра. p50 ниже (запросы раньше берут в работу), но p95 почти вдвое
  хуже (65 мс против 34) из-за пауз на throttling.
- **Итог для 2 CPU / 1 GiB:** оптимум — 2 workers. 4 workers вдвое дороже по
  памяти без выигрыша в RPS и с худшим хвостом задержек.
- Разброс между запусками мал: RPS ±0,1–1,5%, память ±1 MiB.
- Throttling, посчитанный только за основной замер (92%), выше, чем по всему
  времени жизни контейнера (~82% в первом прогоне `results/20261025-194706`):
  в старте и прогреве CPU используется меньше. Поэтому важно, чтобы границы
  метрик совпадали.

`thr s` в `summary.txt` при 4 workers (~96 с за 60-секундный замер) больше
длительности замера, потому что ядро суммирует `throttled_usec` по всем CPU.

```bash
INCLUDE_RESULTS=1 ./scripts/make_archive.sh  # вместе с последним results/<timestamp>
```

## Ограничения эксперимента

- **Модель — это искусственный буфер.** У настоящих фреймворков (PyTorch,
  ONNX Runtime) свои аллокаторы, mmap весов, CUDA-контексты и арены памяти
  потоков. Цифры накладных расходов у них будут другими.
- **Нет разделения памяти.** Схемы с `gunicorn --preload` + fork (CoW), с
  `mmap` файла весов или с shared memory здесь не исследуются. В Python CoW к
  тому же частично ломается из-за счётчиков ссылок.
- **CPU-нагрузка синтетическая.** Чистый Python держит GIL, поэтому внутри
  одного worker'а threadpool не даёт параллелизма. Это намеренно упрощено,
  чтобы масштабировались именно процессы.
- **Генератор нагрузки работает на том же хосте.** Он отнимает CPU у Docker
  VM (на macOS и Windows контейнеры работают внутри Linux VM), поэтому RPS
  относительны: сравнивать их стоит только между прогонами на одной машине.
  `--cpus=2` — это квота CFS, а не выделенные ядра. Возможен throttling, его
  видно в `/sys/fs/cgroup/cpu.stat` (в сводке — за основной интервал).
- **Метрики памяти разные.** `docker stats`, `memory.current` и сумма RSS
  отличаются из-за page cache и общих страниц. Сравнивать стоит одну и ту же
  метрику между запусками. Для лимита важна `memory.current`.
- **`memory.peak`** требует cgroup v2 и ядро ≥ 5.19. На cgroup v1 скрипт
  показывает `max_usage_in_bytes`.
- **Один прогон — это не статистика.** Для выводов стоит повторить прогон 3–5
  раз и смотреть разброс.
